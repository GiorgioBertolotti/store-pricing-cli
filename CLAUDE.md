# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo does

`store-pricing-cli` is a single guided CLI (`pricing.py`) for scaling prices by country (purchasing power parity / PPP adjusted) and pushing them to App Store Connect, Google Play Console, and Stripe. It covers both subscriptions and one-time purchases on all three platforms; a project can configure either, both, or neither per store, independently. Logic lives in the `store_pricing/` package; `pricing.py` is a thin entry point.

```
store_pricing/
  config.py    Settings dataclass: .env + pricing.toml -> passed as a parameter (never module globals)
  data.py      cost-of-living + country-code fetching (World Bank PPP + pycountry/Babel), writes cost_of_living_data.xlsx and country_codes.json
  scaler.py    price scaling math: exchange rates, PPP scaling factor, VAT, psychological rounding -> price_scaled.xlsx
  inputs.py    InputData: loads price_scaled.xlsx + country_codes.json for the apply/offer steps
  google.py    Google Play price updates via the Android Publisher API - subscriptions (basePlans, the 400-error recovery ladder) and one-time products (onetimeproducts/purchaseOptions, same ladder adapted)
  apple.py     App Store Connect price updates via the App Store Connect API - subscriptions (price-point resolution, JWT, startDate retry) and one-time in-app purchases (inAppPurchasePriceSchedules)
  stripe_platform.py  Stripe regional prices via Price.currency_options (per-currency, not per-country - see below) - subscriptions and one-time Prices share this logic since currency_options works identically on both
  offers.py    Promotional/discount offers across all three platforms, built on top of apple.py/google.py/stripe_platform.py - subscriptions only, see "Key design decisions"
  backup.py    snapshots of a Google Play product before a patch, and the before/after comparison
  wizard.py    `setup` (guided credential entry with live API verification) and `doctor` (re-verify without touching .env)
  report.py    Shared failure-report writer
  ui.py        Shared rich/questionary rendering: price preview, live-price diff, confirmations
  cli.py       argparse subcommands + the guided no-args flow
```

`pricing.py` with no arguments runs the guided flow: refresh cached data if stale → run the credential wizard if nothing's configured → prompt for a USD price → preview the computed table → optionally push, showing a diff against what's currently live and requiring confirmation before anything is written. Subcommands (`setup`, `doctor`, `scale`, `apply`, `offer`, `refresh-data`) cover the same ground non-interactively for CI, each falling back to a prompt for any flag left unset.

## Setup

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python pricing.py setup   # or just `python pricing.py` and let the guided flow trigger it
```

## Running the pipeline

```bash
python pricing.py                                          # guided flow
python pricing.py doctor                                    # live-verify configured credentials
python pricing.py scale --price 19.99                       # compute only, no store writes
python pricing.py apply --dry-run                            # resolve everything, push nothing
python pricing.py apply --yes                                 # push live, no confirmation (CI)
python pricing.py apply --apple-iap --google-iap --stripe-onetime --yes  # one-time products only, leaving subscriptions untouched
python pricing.py offer --discount 30 --cycles 3 --period P1M --code SUMMER30 --google-offer-id summer-30-off
python pricing.py refresh-data                               # regenerate cost_of_living_data.xlsx + country_codes.json
python pricing.py backup-google                               # snapshot the Google Play products to backups/ (read-only)
python pricing.py restore-google --backup backups/<file>.json --dry-run   # what a restore would change
```

## Required credentials (`.env`)

Same variable names as before; `pricing.py setup` writes this file for you and live-verifies each value against the real API as it's entered, rather than leaving verification to whenever `apply` first hits the API.

| Variable                             | Source                                                       |
| ------------------------------------ | -------------------------------------------------------------- |
| `GOOGLE_SERVICE_ACCOUNT_FILE`        | Path to `service-account-file.json` from Google Play Console |
| `GOOGLE_PACKAGE_NAME`                | App package name                                             |
| `GOOGLE_SUBSCRIPTION_ID`             | Subscription product ID in Play Console                      |
| `GOOGLE_BASEPLAN_ID`                 | Base plan ID within that subscription                        |
| `GOOGLE_ONETIME_PRODUCT_ID`          | One-time product ID in Play Console (Monetize → Products → One-time products) |
| `GOOGLE_ONETIME_PURCHASE_OPTION_ID`  | Purchase option ID within that product                       |
| `APPLE_ISSUER_ID`                    | App Store Connect → Keys → Issuer ID                         |
| `APPLE_KEY_ID`                       | API key ID                                                   |
| `APPLE_PRIVATE_KEY`                  | Full private key contents (use `\n` for newlines in `.env`)  |
| `APPLE_APP_ID`                       | Numeric App ID (not bundle ID)                               |
| `APPLE_SUBSCRIPTION_PRODUCT_ID`      | Product ID of the subscription in-app purchase               |
| `APPLE_IAP_PRODUCT_ID`               | Product ID of the one-time in-app purchase                   |
| `STRIPE_SECRET_KEY`                  | Secret (`sk_...`) or restricted (`rk_...`) key, write access to Prices/Coupons/Promotion codes |
| `STRIPE_PRICE_ID`                    | Recurring Price ID for this subscription (`price_...`)       |
| `STRIPE_ONETIME_PRICE_ID`            | One-time (`type=one_time`) Price ID (`price_...`)             |

The one-time-product variables are independent of their subscription counterparts - a store's shared account-level vars (`GOOGLE_SERVICE_ACCOUNT_FILE`/`GOOGLE_PACKAGE_NAME`, `APPLE_ISSUER_ID`/`APPLE_KEY_ID`/`APPLE_PRIVATE_KEY`/`APPLE_APP_ID`, `STRIPE_SECRET_KEY`) are reused for both, but the product-identifying vars are separate, so a project can configure a subscription, a one-time product, or both on the same store without one implying the other. `pricing.py setup --google`/`--apple`/`--stripe` asks which product type(s) to configure via a checkbox rather than needing separate `setup` invocations.

`store_pricing/config.py` parses these into `GoogleCreds`/`AppleCreds`/`StripeCreds`/`GoogleOneTimeCreds`/`AppleOneTimeCreds`/`StripeOneTimeCreds` and reports **all** missing/malformed vars at once (not first-failure-only like the old `_validate_env()`), so `Settings.apple_configured`/`.google_configured`/`.stripe_configured`/`.apple_onetime_configured`/`.google_onetime_configured`/`.stripe_onetime_configured` let any subset of these six run without the others' vars being present at all.

`.env` wins for every variable it defines; anything it omits falls through to the **process environment**, so CI can inject these as secrets instead of writing a `.env` file (matching what the pre-package `load_dotenv()` + `os.getenv()` did). Values still set to `.env.example`'s `your_*` placeholders are rejected as unconfigured rather than being passed to the API.

## `pricing.toml`

Generated with commented defaults on first run (see `pricing.toml.example` for the reference copy, or `store_pricing/config.py`'s `TOML_TEMPLATE`). Covers what used to be hardcoded constants: `anchor_country` (`price_scaler.py`'s old `reference_country`), `scaling_cap`, `default_vat` + per-country `[pricing.vat]` overrides, `rounding`, Apple's price-point tolerance (`price_point_tolerance_pct`/`_units`), `apple.max_workers`, and `data.ppp_year`.

Values are validated at load time and raise `ConfigError` naming the offending key, rather than surfacing later as a mid-run crash or a silently wrong price — an unrecognised `rounding` used to fall through to psychological rounding, so a typo looked like it worked, and `max_workers = 0` blew up inside `ThreadPoolExecutor` only once a run was already underway.

## Key design decisions

**Pricing algorithm** (`store_pricing/scaler.py`): scaling factor is capped at `pricing.scaling_cap` (default 1.0) and floored at `pricing.min_scaling_factor` (default 0, off) - the floor exists because World Bank PPP data occasionally comes in a currency other than the one the country is priced in (Liberia's is effectively USD while it's priced in LRD), producing factors like 0.003 — countries more expensive than the anchor country get the full USD price; only cheaper countries get a discount. Formula: `scaled_native = usd_price × scaling_factor × exchange_rate × (1 + vat_rate)`, then smart-pricing rounds to `.99` endings. `apply_smart_pricing()` and `PricingConfig.vat_rate()` are pure functions (no I/O, no side effects) specifically so they're unit-testable — see `tests/test_scaler.py`. The `US_REFERENCE_MEAL_USD` constant in `data.py` (the "meal for 2" PPP anchor) is cosmetic: the scaling factor algebraically reduces to `min(ppp_factor / fx_rate, scaling_cap)` regardless of its value.

**Market ratios** (`[pricing.market_ratio.<plan>]`, selected with `scale --plan weekly|monthly|annual` or a prompt in the guided flow): PPP prices digital subscriptions far below what high-income but lower-PPP markets actually pay (Southern Europe, Japan), so a country listed for the chosen plan is priced at `anchor gross price × ratio` instead, with no VAT added on top since the ratio is tax-inclusive. Countries not listed, or runs without a plan, keep the PPP path. `scale_price()` records which path each row took in `Pricing_Basis`. The optional `[pricing] market_ratio_cap` clamps every ratio in `PricingConfig.market_ratio()`, since market medians across all apps can put a cheap app far above its anchor price in a few countries. Ratio and VAT keys are World Bank country names (the ones in `cost_of_living_data.xlsx`); `run()` prints any market-ratio country the data doesn't know, and `tests/test_scaler.py` checks the built-in VAT table against `country_codes.json` because a non-World-Bank spelling silently falls back to `default_vat`.

**Per-plan rounding** (`[pricing.plan_rounding]`, keyed by the same `--plan`): `psychological-half` adds `.49` endings between 1 and 100, picking the nearest of `x.49`/`x.99`/`(x-1).99`. On a cheap plan a whole-unit `.99` step is 25-50% of the price, enough to undo the market ratio. The mode used is written to the `Rounding` column of `price_scaled.xlsx` and read back by `InputData.rounding`, so the apply-time currency conversions (`convert_to_currency()` for Google's locked currencies and Apple's differing territory currencies, and Apple offers) round the same way the scale step did.

**Apple price matching**: the App Store only allows prices from a fixed set of price points. `get_closest_price_point()` (`store_pricing/apple.py`) finds the nearest available point; it skips if the difference exceeds `pricing.toml`'s `apple.price_point_tolerance_pct`/`_units` (default 10% or 2 units of local currency). This is why some countries appear in failure reports.

**Apple startDate**: price updates need a future `startDate`; "tomorrow" (UTC) is sometimes rejected as still too soon (undocumented minimum lead time, observed requiring at least 2 days) — `_submit_price()` reads Apple's own "must be on or after YYYY-MM-DD" out of the 409 body and retries with that date instead of guessing a fixed offset.

**Apple concurrency**: price-point resolution and live-price fetching are each one HTTP round-trip per country (pure I/O wait), so `apple.update_prices()`, `apple.fetch_live_prices()`, and the resolution loop in `offers.create_apple_offer()` all run through a `ThreadPoolExecutor(max_workers=pricing.apple_max_workers)` instead of a sequential loop — cuts a ~200-country run from minutes (or, for the live-price fetch, a near-hang) to well under a minute. The default of 8 is a deliberately conservative default against Apple's undocumented rate limits; console output from concurrent countries will interleave since prints happen inside worker threads.

**Google Play**: prices are written by patching the full subscription object in-place (not a per-region endpoint), which means every patch resubmits _all_ base plans, not just the one you're targeting — a pre-existing data problem on a base plan you have no intention of touching (e.g. a stale price left over from a currency changeover) can still block the whole patch. Google rejects any price whose currency doesn't match what's already configured for that region (there's no in-place currency change via this endpoint), usually a leftover from an earlier flat-price rollout that never localized. Rather than skip and log a failure the way the pre-package script did, `_update_region()` converts the computed price into whatever currency Google already has on file (`scaler.convert_to_currency()`, shared with Apple's differing-territory-currency retry) and writes that — so those regions now get updated instead of failing every run. Only a region with no available exchange rate still fails; the apply-time diff predicts which is which, showing `fx convert` vs `locked`. The patch loop (`store_pricing/google.py`) auto-retries on recoverable 400 errors (stale currency codes, non-billable regions, price out of range via clamping to Google's minimum). If a clamp is applied to the same (base plan, region) pair twice without Google's validation ever converging, the region is dropped from just that one base plan (not the one being updated) so the rest of the patch can still go through. If Google then rejects _that_ too (`"Regional configs were removed from the base plan"` — confirmed to happen for an existing/active region, unlike a not-yet-configured one), the script gives up immediately with an actionable `RuntimeError` pointing at the specific base plan/region to fix manually in Play Console, rather than retrying blindly — this specific combination is a Google-side data lock the API has no path to resolve.

**Google backups** (`store_pricing/backup.py`): because a Google patch resubmits every base plan / purchase option and the 400 ladder can clamp or drop regions on containers that aren't being priced, a live (non-dry-run) `update_prices()`/`update_onetime_prices()` first writes the product exactly as Google returned it to `backups/` (gitignored) and refuses to patch if that write fails. After the patch it re-reads the product and `backup.compare()` reports, as failures carrying a `restore-google` hint, any price that moved outside the priced container and any region that disappeared from it. `restore-google` patches a backup's containers back with no 400 ladder (a restore lands exactly or not at all), refuses a backup of a different product id, snapshots the live state first so the restore itself is reversible, and re-reads to confirm nothing still differs. Dry-runs never write backups or patch. `tests/test_google_backup.py` runs all of this against an in-memory fake of the Publisher API.

**Google live-price keying**: Google's regional configs are keyed by ISO alpha-2 region code, but everything else in the pipeline (`InputData.country_prices`, the diff table) is keyed by country name — `google.fetch_live_prices()` reverses `country_code_mapping` to translate as it reads, so callers never see the mismatch.

**One-time in-app purchases (Apple)** (`store_pricing/apple.py`): price-point resolution mirrors the subscription path almost exactly (`get_closest_iap_price_point()`/`resolve_iap_price_point()` share their retry-in-Apple's-currency logic with the subscription versions via `_resolve_point()`), just under `/v2/inAppPurchases/{id}/pricePoints` instead of `/v1/subscriptions/{id}/pricePoints`. Writing prices is structurally different, though: an in-app purchase has exactly one `InAppPurchasePriceSchedule`, and the only documented way to change it is `POST /v1/inAppPurchasePriceSchedules` with a `manualPrices` entry for *every* territory being priced in one request - there's no per-territory PATCH the way `subscriptionPrices` has. `update_iap_prices()` is therefore all-or-nothing at the HTTP level: it resolves every country's price point concurrently (same `ThreadPoolExecutor` pattern as subscriptions) but submits one POST covering the whole batch, and a rejection fails every territory that was in that batch, not just one. The payload also requires a `baseTerritory` relationship, which has no independent meaning in this pipeline beyond "which territory anchors the schedule" - `pricing.toml`'s `anchor_country` fills that role. This shape was confirmed against Apple's official OpenAPI spec (cross-checked via `github.com/EvanBacon/App-Store-Connect-OpenAPI-Spec`, since developer.apple.com's docs pages are JS-rendered and not fetchable directly), but - unlike the subscription-offers payload in `offers.py` - hasn't been exercised against a live schedule that already has prices, so a second POST replacing an existing schedule isn't confirmed live; `tests/test_apple_iap_payload.py` locks down the payload shape that *is* documented.

**One-time products (Google)** (`store_pricing/google.py`): uses the newer `monetization.onetimeproducts` resource rather than the legacy `inappproducts` one. It mirrors the subscription shape closely enough to reuse most of the same patch/retry machinery: a `OneTimeProduct`'s `purchaseOptions` array plays exactly the role `basePlans` does for a `Subscription`, and each purchase option's `regionalPricingAndAvailabilityConfigs` is the same per-region `price: Money` shape as a base plan's `regionalConfigs` - `_update_onetime_region()`/`patch_onetime_with_currency_fixes()`/`_handle_onetime_400_error()` are the one-time-product siblings of the subscription functions they're named after. The 400-error recovery ladder is reused where Google's error wording is product-agnostic (currency mismatch, non-billable region, price out of range - `_CURRENCY_MISMATCH_RE`/`_NOT_BILLABLE_RE`/`_PRICE_OUT_OF_RANGE_RE` are shared verbatim); only the "regional configs were removed" message names "purchase option" instead of "base plan" for this product type, so it gets its own regex (`_PURCHASE_OPTION_REMOVAL_REJECTED_RE`) - unverified against a live 400, so an unrecognised wording falls through and re-raises rather than mishandling it, same as today's unrecognised-error fallback. `OneTimeProduct.regionsVersion` is the `{"version": "..."}` object form per Google's schema (unlike `Subscription.regionsVersion`, read as a bare string) - `fetch_onetime_product()` reads the nested field.

**Promotional offers stay subscription-only**: `pricing.py offer` (percentage off for N billing cycles) has no direct analogue for a one-time purchase - there's no recurring price to discount, Google Play's one-time-product API (as of this writing) has no promotional-offer sub-resource comparable to a subscription base plan's `offers`, and a Stripe Coupon's `duration_in_months` needs a recurring billing cadence to discount across. `_available_offer_platform_names()` (`cli.py`) deliberately excludes the one-time targets from `offer`'s platform picker rather than silently no-op'ing if selected.

**Country code mapping**: `country_codes.json` maps World Bank country names → ISO alpha-2 (Google) and alpha-3 (Apple). `store_pricing/data.py`'s `refresh_country_codes()` (formerly `update_country_codes.py`) regenerates this file from the World Bank API (alpha-2 + names) and `pycountry` (alpha-3, offline), merge-only — existing entries are never dropped. restcountries.com's free v3.1 API was retired (301s to a deprecated-endpoint error body); its v5 replacement requires a signed-up API key, so both this and `data.py`'s currency-code lookup were moved off it entirely onto offline datasets (`pycountry` + Babel's CLDR territory data) rather than adding a new required credential.

**Stripe** (`store_pricing/stripe_platform.py`): Stripe has no per-country pricing like Apple/Google — a Price only supports per-*currency* overrides via `currency_options`, and a Price's own default currency/amount is immutable once created (Stripe Prices in general can't be edited in place). So this module prices by currency, not by country: every country sharing a currency gets that currency's one Stripe amount, and countries priced in the base Price's own currency are reported back as `locked` (same concept as Google's currency-locked regions) — updating those needs a new Price and a `STRIPE_PRICE_ID`/`STRIPE_ONETIME_PRICE_ID` change, not an API call. Where PPP scaling wants different prices for countries that share a currency (the eurozone being the common case), `resolve_currency_options()` picks the anchor country's price if the anchor is in that currency group (so the currency the anchor itself is priced in is never discounted), otherwise averages the group. `update_prices()` patches all currencies in one `Price.update` call and, on a Stripe error naming a specific `currency_options[xxx]` param (read off the exception's `.param`, not string-matched against the message), drops just that currency and retries — mirroring Google's per-region 400 recovery, but per-currency instead of per-region.

`currency_options` doesn't care whether the underlying Price is recurring or `type=one_time` - Stripe applies the same mechanism to both - so one-time-purchase support (`update_onetime_prices()`/`fetch_live_onetime_prices()`) is a thin wrapper: `_update_prices_for()`/`_fetch_live_prices_for()` hold the shared logic, parameterized only by which of `fetch_price()`/`fetch_onetime_price()` validates the Price's recurring-vs-one-time-ness (`_fetch_price(creds, require_recurring=...)`) and which platform label (`"Stripe"` vs `"Stripe (One-time)"`) its failures get tagged with.

**Distinct platform labels for subscription vs one-time failures**: every one-time price-update function (`apple._make_iap_failure()`, `google._make_onetime_failure()`, `stripe_platform._make_onetime_failure()`) tags its failures with a platform string distinct from its subscription counterpart (`"Apple App Store (One-time)"` vs `"Apple App Store"`, etc.) rather than reusing the bare `_make_failure()` helper. `report.write_failure_report()` and `ui.failure_summary_table()` both group failures by that exact string - without the distinct label, a single `apply` run covering both a subscription and its one-time counterpart on the same store would merge their failures into one indistinguishable bucket, with no way to tell from the report which product a given failure belonged to. The report only shows the `(SUBSCRIPTION)`/`(ONE-TIME)` qualifier when both are present in the same run; a subscription-only (or one-time-only) run's report looks exactly as it did before this distinction existed.

**Promotional offers** (`store_pricing/offers.py`): `pricing.py offer` prompts first for which platform(s) to target (any subset of Apple/Google/Stripe that's configured), then for the fields it needs. Google Play offers use `relativeDiscount` (a percentage off whatever price is currently live per region), so no price computation is needed there; regions Google reports as "not billable" or with the discounted price "out of range" are auto-dropped and retried (same pattern as the base price applier's 400-error recovery, reusing `google._NOT_BILLABLE_RE`). Apple has no percentage-discount concept — the code computes a discounted price from `Smart_Price_Native`, resolves it to a price point via `apple.resolve_price_point()` (reused from the base price path, so the USD-retry fallback for territories Apple prices in USD applies here too), then sends it as a JSON:API compound document: the `prices` relationship references client-chosen ids wrapped as `${local-id}` (e.g. `${NOR}`), and a top-level `included` array supplies each one's `subscriptionPricePoint` + `territory` relationships. This endpoint is thinly documented by Apple and its runtime validation (the `${...}` id wrapping, the required `included` block) isn't reflected in Apple's own published OpenAPI schema — the shape was reverse-engineered from the live 409 error responses, not official docs; `tests/test_apple_payload.py` locks the shape down. Apple's PATCH endpoint for this resource rejects the same payload shape its POST endpoint accepts (also undocumented) — since only POST is proven to work, re-running with the same `offerCode` deletes the existing offer and fully recreates it via POST rather than extending it in place, at the cost of a brief window where the offer doesn't exist; `offers.find_existing_apple_offer()` is exposed separately so the CLI can warn and confirm _before_ committing to that. Apple additionally never frees up a `name`/`offerCode` once used, even after the offer is deleted (also undocumented) — a duplicate-attribute 409 on that recreate POST is auto-retried with a `-<unix timestamp>` suffix appended to both, rather than failing outright. Stripe has no percentage-off-current-price concept either, but unlike Apple its Coupon `percent_off` applies uniformly regardless of currency, so no per-country resolution is needed — `create_stripe_offer()` creates a `Coupon` (`duration="repeating"`, `duration_in_months` = billing-period months × cycles; a weekly period has no whole-month equivalent and is rejected up front rather than sent to Stripe) plus a `PromotionCode` referencing it, reusing `--code` as both the coupon id and the customer-facing promo code. Coupons are immutable and Stripe's delete-then-recreate semantics for one still referenced by a Promotion Code aren't documented, so — unlike Apple's delete-and-recreate — a duplicate id/code on re-run is instead retried with the same `-<unix timestamp>` suffix pattern as Apple's duplicate-attribute case, leaving the old coupon/code in place alongside the new one.

## Tests

`tests/` covers the pricing math (`test_scaler.py`), Google's 400-error recovery ladder for both subscriptions and one-time products (`test_google_errors.py`/`test_google_onetime_errors.py`), the Apple promotional-offer payload shape and the one-time in-app-purchase price-schedule payload shape (`test_apple_payload.py`/`test_apple_iap_payload.py`), Stripe's currency-collision resolution and per-currency retry ladder for both subscription and one-time Prices (`test_stripe_platform.py`), credential resolution including the independent one-time-product vars (`test_config.py`), the distinct subscription-vs-one-time platform labels in the failure report (`test_failure_report_labels.py`), and PPP-year fallback + country-code merge semantics (`test_data.py`). Run with `pytest` after `pip install -r requirements-dev.txt`. These are pure-logic tests with network calls monkeypatched out — they don't touch the real APIs.
